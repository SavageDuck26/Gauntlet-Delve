0. BUNDLE SIGNATURE COMPARISON (NEW - January 16, 2026)
================================================================================

Three bundle formats have been identified across Bitsquid/Stingray games:

SIGNATURE 0xF0000004 - "OLD" FORMAT (Gauntlet uses this)
---------------------------------------------------------
- Used by: Gauntlet Slayer Edition (2014), early Bitsquid games
- Name hash table: Present (sorted hashes for quick lookup)
- Entry table: 16 bytes per entry (type_hash + name_hash)
- Resource headers: 36 bytes (type, name, flags, stream_size, main_size, unknown)
- Resource data: Stored directly (DDS textures start with "DDS " magic)
- Compression: Zlib, 64KB chunks

SIGNATURE 0xF0000005 - "NEW" FORMAT
---------------------------------------------------------
- Used by: Later Bitsquid/Stingray games
- Similar to 0xF0000004 but with additional metadata

SIGNATURE 0xF0000006 - "MOD" FORMAT (Vermintide 2)
---------------------------------------------------------
- Used by: Vermintide 2 mod_bundle files
- Name hash table: Zeros (placeholder, not used)
- Entry table: 24 bytes per entry (type, name, flags, size - NO separate header)
- Resource data: Follows directly after entry table
- Textures: Have custom header (~1500 bytes) before DDS data
- Compression: Same zlib, 64KB chunks

CRITICAL DIFFERENCE FOR MODDING:
  - Gauntlet (0xF0000004): Textures stored as RAW DDS files
  - Vermintide (0xF0000006): Textures have custom header before DDS data
  
  This means you CANNOT directly use a Vermintide mod_bundle in Gauntlet!
  You must use the Gauntlet format (0xF0000004) for Gauntlet mods.

1. OVERVIEW
================================================================================

Gauntlet Slayer Edition uses the Bitsquid engine (later renamed Stingray, now 
discontinued by Autodesk). The game stores all assets in "bundle" files which 
are zlib-compressed containers holding multiple resources.

Key characteristics:
- All resource names are hashed using MurmurHash64
- Bundle files are zlib compressed in 64KB chunks
- Resources include textures, materials, units, Lua scripts, etc.
- The bundle_database.data file maps resources to bundles
- Some bundles have associated .stream files for large data (textures)

2. FILE LOCATIONS
================================================================================

Game Installation:
  C:\Program Files (x86)\Steam\steamapps\common\Gauntlet\

Key Directories:
  contents/                  - All bundle files and database
  contents/bundle_database.data  - Resource-to-bundle mapping
  contents/dlc/              - DLC bundle files
  binaries/                  - Game executable and DLLs

Bundle Files:
  Named with 16 hex characters (MurmurHash64 of original name)
  Example: 0164ad48615ba9ed
  
Stream Files:
  Same name as bundle with .stream extension
  Example: 0164ad48615ba9ed.stream
  Contains large resource data (primarily textures)

Total bundles found: 77 (main game, not counting DLC)

================================================================================
3. BUNDLE FILE FORMAT (COMPRESSED)
================================================================================

Header (12 bytes):
  Offset 0x00: uint32 - Signature
                        0xF0000004 = "OLD" format (Gauntlet uses this)
                        0xF0000005 = "NEW" format (later Bitsquid games)
  Offset 0x04: uint32 - Uncompressed size in bytes
  Offset 0x08: uint32 - Padding (always 0)

Data:
  Sequence of zlib-compressed chunks, each prefixed with 4-byte size
  
  For each chunk:
    uint32 - Compressed chunk size
    bytes  - Zlib compressed data (deflate)
  
  Chunks decompress to 64KB (0x10000 bytes) each
  Last chunk may be smaller

Example:
  File: 0bd097fa120382fe
  Compressed size: 2,852,372 bytes
  Uncompressed size: shown in header

4. UNPACKED BUNDLE FORMAT  *** CORRECTED May 2026 — Prior version was WRONG ***
================================================================================

After decompression, the bundle body has this exact layout.
All offsets are confirmed by byte-level comparison against native game bundles.

────────────────────────────────────────────────────────────
[0x000:0x004]  uint32  N  — resource count
────────────────────────────────────────────────────────────
[0x004:0x058]  84-byte PREAMBLE
    Native bundles:  opaque data (some kind of hash or fingerprint)
    Custom bundles:  all zeros (engine does not validate this region)

[0x058:0x104]  172-byte PADDING (zeros)
────────────────────────────────────────────────────────────
[0x104:]       TOC — (N+1) × 16-byte entries
    Each entry: {uint64 type_hash, uint64 name_hash}
    IMPORTANT: entry[N] is a SENTINEL = exact copy of entry[0]
               (the engine relies on this sentinel; omitting it corrupts the file)
────────────────────────────────────────────────────────────
[toc_end:]     RESOURCE-0 METADATA — 20 bytes  ← DIFFERENT from resources 1..N-1!
    uint32  flags       (normally 1)
    uint64  zeros       (always 0)
    uint32  data_sz     (byte count of resource-0 data that follows)
    uint32  stream_sz   (0 = no stream, or size of associated .stream data)

[toc_end+20:]  RESOURCE-0 DATA — data_sz bytes
────────────────────────────────────────────────────────────
[after res-0:] RESOURCES 1..N-1  (each starts with a 36-byte header)
    Each resource:
      uint64  type_hash   (same as its TOC entry)
      uint64  name_hash   (same as its TOC entry)
      uint32  flags       (normally 1)
      uint64  zeros       (always 0)
      uint32  data_sz
      uint32  stream_sz
      bytes[data_sz]  resource data
────────────────────────────────────────────────────────────

KEY DIFFERENCES FROM PRIOR DESCRIPTION (CORRECTIONS):

  WRONG (old): "Name hash table at bytes 4..104"
  RIGHT:       bytes 4..104 are an opaque preamble; no hash table exists

  WRONG (old): "Entry table has N entries"
  RIGHT:       Entry table has N+1 entries — entry[N] is a sentinel copy of entry[0]

  WRONG (old): "All resources have 36-byte headers"
  RIGHT:       Resource-0 has a 20-byte header (no type/name, just flags/zeros/sizes)
               Resources 1..N-1 have the full 36-byte header

  WRONG (old): "stream_size field is stream FILE size for whole bundle"
  RIGHT:       stream_sz in the per-resource header is specific to that resource's
               streaming data, not a global bundle-level field

FORMULA:
  toc_end = 0x104 + (N+1) * 16
  res0_data_start = toc_end + 20

EXAMPLE (bundle 96438abc757b9f23, N=1):
  [0x000] N=1
  [0x104] TOC[0]: type=0x27862fe24795319c  name=0x96438abc757b9f23
  [0x114] TOC[1]: type=0x27862fe24795319c  name=0x96438abc757b9f23  ← sentinel
  [0x124] Resource-0 hdr: flags=1 zeros=0 data_sz=220 stream_sz=0
  [0x138] Resource-0 data: 220 bytes of render_config COBJ blob

6. BUNDLE_DATABASE.DATA FORMAT
================================================================================

This file maps resources to their bundle files.

Header (8 bytes):
  Offset 0x00: uint32 - Version (2 for Gauntlet)
  Offset 0x04: uint32 - Total entry count (14553 for Gauntlet)

Entries (52 bytes each):
  Offset 0x00: uint32 - Platform ID (1 = common?)
  Offset 0x04: uint32 - Bundle name length (16 for hex names)
  Offset 0x08: char[] - Bundle name (16 hex characters)
  Offset 0x18: uint32 - Stream name length (23 for "name.stream\0")
  Offset 0x1C: char[] - Stream filename (null-terminated)

Structure:
  - Entries are grouped by bundle (189 entries per bundle)
  - 77 bundles × 189 entries ≈ 14553 total
  - Each group of 189 entries maps resources to one bundle

Bundle Priority:
  According to dev info: Bundles listed later in the database take 
  precedence over earlier ones. This can be exploited for modding
  by adding modified bundles at the end of the database.

7. STREAM FILES
================================================================================

Stream files (.stream) contain large binary data, primarily AUDIO streams
(Ogg Vorbis format) and possibly large texture mipmaps.

CRITICAL DISCOVERY (Updated):
  The stream_size field in each resource's 36-byte header is NOT the size
  of that resource's streaming data. Instead, it equals the TOTAL size of
  the .stream file when the bundle has associated streaming data.
  
  Example: In 0164ad48615ba9ed (which has a 22,590,612 byte .stream file),
  ALL 464 textures have stream_size = 22,590,612, even though most textures
  have their complete data in the main bundle.

STREAM FILE CONTENTS:
  - Primarily OGG VORBIS AUDIO (detected by "OggS" magic)
  - The .stream file for 0164ad48615ba9ed contains 5,656 OggS chunks
  - Stream files are NOT zlib compressed (raw binary data)
  
RESOURCE TYPES THAT USE STREAMING:
  Resource Type           In main bundle only   Uses .stream
  ----------------------------------------------------------------
  texture                 Yes (full DDS)        Rare/TBD
  material                Metadata only         No
  unit                    Full data             No
  wwise_stream            Header only           Yes (audio)
  wwise_bank              Full data             No
  particles               Metadata              Possibly
  
Bundles WITH stream files:
  - 0164ad48615ba9ed.stream (22,590,612 bytes) - Audio/Level data
  - 2dcf25b90002fc07.stream (6,468,154 bytes)  - Audio
  - 099d12829b617a9b.stream (17,983,567 bytes) - Audio
  - 0f07a1cb5132485b.stream (33,396,922 bytes) - Audio
  
Bundles WITHOUT stream files (SAFE TO MODIFY):
  - 07c9b8511b5aff2e - Menu/UI textures 
  - 07cdebae91f29fae - Lobby/character textures 
  - 0bd097fa120382fe - Additional resources 
  - Many smaller bundles 

MODDING IMPLICATIONS:
  1. The stream_size field MUST match the .stream file size (or be 0)
  2. Textures in bundles WITH .stream files have complete DDS data
     in the main bundle - the stream file is for AUDIO, not textures
  3. When modifying bundles with .stream files:
     - Keep stream_size unchanged (= .stream file size)
     - Do NOT delete or modify the .stream file
     - Texture data can be replaced in main bundle
  4. If a level hangs while loading, check:
     - Is the .stream file present and unchanged?
     - Do all resources have correct stream_size values?
     - Is the bundle properly compressed with correct header?

TESTING RESULTS (Updated):
  - Menu bundles (no stream): Modification works ✓
  - Lobby bundles (no stream): Modification works ✓  
  - Level bundles (with stream): Need more testing with stream_size preserved

8. TEXTURE FORMAT (DDS)
================================================================================

Textures are stored in DirectDraw Surface (DDS) format.

DDS Header (128 bytes minimum):
  Offset 0x00: char[4] - Magic "DDS "
  Offset 0x04: uint32  - Header size (124)
  Offset 0x08: uint32  - Flags
  Offset 0x0C: uint32  - Height
  Offset 0x10: uint32  - Width
  Offset 0x14: uint32  - Pitch or linear size
  Offset 0x18: uint32  - Depth
  Offset 0x1C: uint32  - Mipmap count
  ...
  Offset 0x54: char[4] - FourCC format code

Common formats in Gauntlet:
  DXT1 - BC1 compression (8 bytes per 4x4 block, no alpha)
  DXT5 - BC3 compression (16 bytes per 4x4 block, with alpha)
  ATI2 - BC5 compression (16 bytes per 4x4 block, normal maps)

Normal Map Handling:
  Normal maps use ATI2/BC5 format (two-channel RG compression).
  The blue channel must be reconstructed: B = sqrt(1 - R² - G²)
  Normals are stored in [0,1] range and must be remapped to [-1,1].

Textures found in test bundle:
  - 128x128 DXT5 (common for character/item textures)
  - 256x256 DXT5 (larger detail textures)
  - 64x64 DXT1 (smaller/simpler textures)
  - Various other sizes for different purposes

9. UNIT/MESH FORMAT (3D MODELS) - COMPLETE SPECIFICATION
================================================================================

Unit files (.unit) contain 3D mesh data for the Stingray/Bitsquid engine.
This format was fully reverse-engineered using the Helldivers 2 Extractor
(FileDiver) codebase as reference, which uses a newer version of the same engine.

--------------------------------------------------------------------------------
9.1 OVERVIEW
--------------------------------------------------------------------------------

A .unit file contains:
  - Multiple meshes (LOD levels, separate objects)
  - Interleaved vertex data (positions, normals, UVs, bone data)
  - Index buffer (triangle connectivity)
  - Shapes/submeshes (material-based groupings)
  - Material name references
  - Bounding box information

Key differences from Helldivers 2 (newer Stingray):
  - Gauntlet embeds mesh data inline; HD2 uses separate geometry_group files
  - Gauntlet uses simple float32 vertex formats; HD2 uses packed/half-float
  - Gauntlet has no Main/GPU stream split; all data in single file
  - HD2 uses octahedral normal encoding (R10G10B10A2); Gauntlet uses float32[3]

--------------------------------------------------------------------------------
9.2 COMPLETE FILE STRUCTURE
--------------------------------------------------------------------------------

HEADER (8 bytes):
  Offset 0x00: uint32 - Signature (0x00010090 for Gauntlet)
  Offset 0x04: uint32 - Mesh count

PER-MESH STRUCTURE (repeated for each mesh):

  ┌─────────────────────────────────────────────────────────────────────────────
  │ VERTEX BUFFER SECTION
  ├─────────────────────────────────────────────────────────────────────────────
  │ uint32           vertex_buffer_size    Total bytes of raw vertex data
  │ bytes[size]      vertex_data           Interleaved vertex attributes
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ PADDING
  ├─────────────────────────────────────────────────────────────────────────────
  │ 8 bytes          zeros                 Alignment padding
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ MESH METADATA
  ├─────────────────────────────────────────────────────────────────────────────
  │ uint32           vertex_count          Number of vertices
  │ uint32           vertex_stride         Bytes per vertex (56, 64, 72, 88, 96)
  │ uint32           element_count         Number of vertex attributes
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ ELEMENT DESCRIPTORS (repeated element_count times)
  ├─────────────────────────────────────────────────────────────────────────────
  │ uint32           element_type          See Element Type table below
  │ uint32           element_size          Component count - 1 (2 = 3 components)
  │ uint32           layer                 UV layer or bone influence index
  │ uint32           format                Data format (usually 0 for float32)
  │ uint8            end_marker            Terminator byte
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ PADDING
  ├─────────────────────────────────────────────────────────────────────────────
  │ 12 bytes         zeros                 Alignment padding
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ INDEX BUFFER SECTION
  ├─────────────────────────────────────────────────────────────────────────────
  │ uint32           total_index_count     Total number of indices
  │ uint32           index_buffer_size     Size in bytes (count × 2 for uint16)
  │ uint16[count]    indices               Triangle vertex indices
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ SHAPES/SUBMESHES SECTION
  ├─────────────────────────────────────────────────────────────────────────────
  │ uint32           shape_count           Number of submeshes
  │ For each shape (16 bytes):
  │   uint32         material_index        Index into materials array
  │   uint32         index_offset          Starting index in buffer
  │   uint32         index_count           Number of indices (triangles × 3)
  │   uint32         shape_index           Submesh identifier
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ BOUNDING BOX (28 bytes)
  ├─────────────────────────────────────────────────────────────────────────────
  │ float32[3]       min_bounds            Minimum X, Y, Z coordinates
  │ float32[3]       max_bounds            Maximum X, Y, Z coordinates
  │ float32          radius                Bounding sphere radius (or padding)
  │
  ├─────────────────────────────────────────────────────────────────────────────
  │ MATERIALS SECTION
  ├─────────────────────────────────────────────────────────────────────────────
  │ uint32           material_count        Number of materials
  │ For each material:
  │   uint32         string_length         Length of material name
  │   char[length]   material_name         Material resource name
  └─────────────────────────────────────────────────────────────────────────────

--------------------------------------------------------------------------------
9.3 ELEMENT TYPES (VERTEX ATTRIBUTES)
--------------------------------------------------------------------------------

Value  Name          Typical Size   Format              Description
─────────────────────────────────────────────────────────────────────────────────
0      POSITION      12 bytes       float32[3]          Vertex XYZ coordinates
1      NORMAL        12 bytes       float32[3]          Surface normal vector
2      TANGENT       12 bytes       float32[3]          Tangent vector for TBN
3      BINORMAL      12 bytes       float32[3]          Binormal/bitangent vector
4      UV_COORDS     8 bytes        float32[2]          Texture UV coordinates
5      COLOR         16 bytes       float32[4]          Vertex color RGBA
6      BONE_INDICES  4-16 bytes     uint8[4]/uint32[4]  Bone IDs for skinning
7      BONE_WEIGHTS  4-16 bytes     float32[1-4]        Bone influence weights

Element Size Field Interpretation:
  - For Position/Normal/Tangent/Binormal: size = 2 means 3 components (size+1)
  - For UV: size = 1 means 2 components
  - For Bone data: size indicates format variant
    - size = 0: 4 bytes (packed or single weight)
    - size = 2: 12 bytes (3 weights/indices as float32)

--------------------------------------------------------------------------------
9.4 COMMON VERTEX STRIDES
--------------------------------------------------------------------------------

Stride   Elements                                          Typical Usage
─────────────────────────────────────────────────────────────────────────────────
56 bytes Position + Normal + Tangent + Binormal + UV       Simple static mesh
64 bytes Position + Normal + Tangent + Binormal + UV×2     Two UV channels
72 bytes Pos + Norm + Tang + Binorm + UV×2 + Bone(small)   Simple skinned
88 bytes Pos + Norm + Tang + Binorm + UV×2 + Bone(full)    Full skinned mesh
96 bytes All attributes including color                    Maximum data

Calculation: Sum of all element byte sizes must equal stride
  Position:    12 bytes
  Normal:      12 bytes
  Tangent:     12 bytes
  Binormal:    12 bytes
  UV (×1):     8 bytes
  UV (×2):     16 bytes (8 per layer)
  Color:       16 bytes
  Bone Idx:    4-16 bytes
  Bone Wgt:    4-16 bytes

--------------------------------------------------------------------------------
9.5 VERTEX DATA LAYOUT (INTERLEAVED)
--------------------------------------------------------------------------------

Vertices are stored interleaved - all attributes for vertex 0, then vertex 1, etc.

Example for stride=88 (Position + Normal + Binormal + Tangent + UV×2 + Bones):

  Vertex 0 [88 bytes]:
    ├── bytes 0-11:   Position (float32 × 3)
    ├── bytes 12-23:  Normal (float32 × 3)
    ├── bytes 24-35:  Binormal (float32 × 3)
    ├── bytes 36-47:  Tangent (float32 × 3)
    ├── bytes 48-55:  UV Layer 0 (float32 × 2)
    ├── bytes 56-63:  UV Layer 1 (float32 × 2)
    ├── bytes 64-75:  Bone Weights (float32 × 3)
    └── bytes 76-87:  Bone Indices (uint32 × 3)
  
  Vertex 1 [88 bytes]:
    └── [Same layout repeated]

Total vertex buffer size = vertex_count × stride

--------------------------------------------------------------------------------
9.6 INDEX BUFFER FORMAT
--------------------------------------------------------------------------------

Indices define triangle connectivity using vertex references.

Index Format:
  - Gauntlet uses 16-bit (uint16) indices
  - Maximum 65,535 vertices per mesh
  - Stored as little-endian
  
Index Stride Detection:
  index_stride = index_buffer_size / total_index_count
  - 2 bytes = uint16 indices (Gauntlet)
  - 4 bytes = uint32 indices (larger meshes, HD2)

Triangle Winding:
  - Indices are in groups of 3 (triangle list format)
  - Counter-clockwise winding (CCW) for front faces
  - For OBJ export, may need to flip to clockwise for some viewers

--------------------------------------------------------------------------------
9.7 SHAPES AND SUBMESH COVERAGE
--------------------------------------------------------------------------------

Shapes define which portions of the index buffer belong to each material.
IMPORTANT: Shapes often don't cover ALL indices!

Coverage Issue:
  Many .unit files have indices not covered by any shape. These uncovered
  indices may represent:
  - LOD (Level of Detail) geometry
  - Shadow meshes
  - Collision geometry
  - Effects or decals
  
Example from 0x115530e5ba448e08.unit:
  Total indices: 9,258
  Shape 0 covers: indices 0-3,085 (3,086 indices)
  Uncovered: indices 3,086-9,257 (6,172 indices)
  
Solution: Create "synthetic shapes" for uncovered index ranges to ensure
complete geometry extraction.

--------------------------------------------------------------------------------
9.8 COORDINATE SYSTEM
--------------------------------------------------------------------------------

Gauntlet/Stingray uses:
  - Y-up coordinate system
  - Right-handed coordinates
  - UV origin at top-left (V flipped for OBJ export)

For OBJ export:
  - Flip V coordinate: v_obj = 1.0 - v_stingray
  - Position/normal coordinates unchanged
  
For glTF export (if implementing):
  - Apply rotation: -90° around X axis
  - Then rotate around Z if needed
  - glTF is Y-up but uses different handedness

--------------------------------------------------------------------------------
9.9 MATERIALS
--------------------------------------------------------------------------------

Material names are stored as strings referencing material resources.
Examples found in Gauntlet:

Character Materials:

9A. MATERIAL FORMAT (NEW DISCOVERY)
================================================================================

Material files (.material) define how textures are applied to 3D models.
The Gauntlet material format is an older Bitsquid variant (2014).

--------------------------------------------------------------------------------
9A.1 FILE STRUCTURE
--------------------------------------------------------------------------------

HEADER (24 bytes):
  Offset 0x00: uint32 - Version (always 0x0A)
  Offset 0x04: uint32 - Section count (number of material variants/passes)
  Offset 0x08: uint64 - Shader/Base material hash
  Offset 0x10: uint64 - Zero padding

BODY:
  Contains texture slot definitions and material properties.
  
  Texture Slot Entry (16 bytes):
    uint32  - Slot index (0-15)
    uint32  - ThinHash (texture slot type identifier)
    uint64  - Texture resource hash (MurmurHash64 of texture path)

--------------------------------------------------------------------------------
9A.1.1 MINIMAL TEXTURE-BEARING MATERIAL (52 bytes) - CRITICAL DISCOVERY!
--------------------------------------------------------------------------------
Updated: January 10, 2026

When creating custom materials for icons/GUI, use this 52-byte format!

The smallest working material with a diffuse_map texture is 52 bytes.
Example: 495bf47a4c60ca4d.material

STRUCTURE (52 bytes):
  [0:4]   uint32: version      = 0x0A (10)
  [4:8]   uint32: sections     = 1
  [8:16]  uint64: shader_hash  = 0xBA25DE3579DC6624 (diffuse shader)
  [16:24] uint64: padding      = 0
  [24:28] uint32: slot_index   = 1 (MUST BE 1, NOT 0!)
  [28:32] uint32: thin_hash    = 0x3AA8B87E (diffuse_map)
  [32:40] uint64: texture_hash = <your texture hash>
  [40:52] 12 bytes: zeros

CRITICAL NOTES:
  1. Slot index MUST be 1, not 0! This was the root cause of crashes.
  2. Shader 0xBA25DE3579DC6624 supports diffuse_map textures.
  3. The 48-byte GUI shader (0x35AAF8BA4EF11D9E) does NOT have a texture slot!
  4. For icons/bg_img, the material name hash is what Gui.material() looks for.

WORKING SHADERS FOR TEXTURES:
  0xBA25DE3579DC6624 - Simple diffuse (52-byte format, recommended)
  0x5EEF29E143D1CA88 - GUI icons (72-byte format)
  
NON-WORKING FOR TEXTURES:
  0x35AAF8BA4EF11D9E - Pure GUI shader (48 bytes, NO texture slot!)
  0x3100C3D2093FC934 - Shader-only (48 bytes, settings only)

9B. PACKAGE RESOURCE FORMAT  *** CORRECTED May 2026 — Prior 20-byte format was WRONG ***
================================================================================

Package resources (.package) define which resources should be loaded together.
The engine loads packages via Lua: `Game:load_package("resource_packages/name")`

**SUCCESSFULLY TESTED**: Custom texture packages can be loaded at runtime!

--------------------------------------------------------------------------------
9B.1 PACKAGE RESOURCE DATA STRUCTURE  *** CORRECTED ***
--------------------------------------------------------------------------------

CONFIRMED correct format, verified byte-for-byte against native bundle
b22560b172a4cff8 (which contains 5 entries × 28 bytes + 4 + 1 = 145 bytes total).

HEADER (4 bytes):
  uint32  entry_count  — number of resources in package

ENTRIES (28 bytes each):
  uint64  type_hash    — MurmurHash64 of type name (e.g. 0xCD4238C6A0C69E32)
  uint64  name_hash    — MurmurHash64 of resource path
  uint32  c1           — ALWAYS 2 in every native package examined
  uint32  c2           — per-package constant (probably MurmurHash32 of internal
                         package path). Safe to use 0 for custom bundles —
                         engine does NOT validate this at runtime.
  uint32  name_hi32    — upper 32 bits of name_hash (i.e. name_hash >> 32)

TRAILER (1 byte):
  0x01   — always 0x01 in native bundles (not 0x00 as previously documented)

TOTAL SIZE:  4 + (N × 28) + 1  bytes

Example (native bundle b22560b172a4cff8, 5 entries):
  4 + (5 × 28) + 1 = 145 bytes ✓ (matches file size)

WRONG (old 20-byte format, now discarded):
  Old description had:  {type(8), name(8), dep_count(4)} + uint32[] deps
  This was reverse-engineered from wrong assumptions. The dep_count field
  does not exist; bytes 17-28 are c1/c2/name_hi32 fields.

--------------------------------------------------------------------------------
9B.2 THE c2 FIELD
--------------------------------------------------------------------------------

c2 is constant across all entries in a single package, but differs between
packages in the same bundle. Best hypothesis: MurmurHash32 of the internal
package path string (e.g. "resource_packages/scripts_base").

For custom bundles, c2=0 is safe — engine does not validate it at runtime.
The c1 field is ALWAYS 2; meaning is unknown but required.

--------------------------------------------------------------------------------
9B.3 BUNDLE DATABASE REGISTRATION
--------------------------------------------------------------------------------

Custom bundles MUST be registered in bundle_database.data!

Format of bundle_database.data:
  Header:
    uint32: version (observed: 6)
    uint32: entry_count
  
  Entries (variable size each):
    uint32: flags (observed: 1 or 3)
    uint32: bundle_name_length (NOT including null terminator)
    char[]: bundle_name (ASCII, NOT null-terminated in length count)
    uint32: stream_name_length (0 if no stream file)
    char[]: stream_name (if stream_name_length > 0)
    byte:   null terminator (0x00) - CRITICAL!

  **CRITICAL BUG FIX**: Each entry ends with a single null byte (0x00).
  The parser must skip this byte when reading entries!

Adding a new bundle:
  1. Parse existing database to get current entry count
  2. Increment entry count in header
  3. Append new entry for each resource in your bundle
  4. Each entry: flags + bundle_name_len + bundle_name + stream_len + [stream] + 0x00

Tool: add_bundle_to_db.py handles this correctly.

9B.5 BUNDLE FORMAT FOR PACKAGES  *** CORRECTED (same correction as Section 4) ***
--------------------------------------------------------------------------------

Use the CONFIRMED layout from Section 4. The old description below is WRONG and
replaced here for clarity:

WRONG OLD FORMAT (discarded):
  "name hash table at 0x04, entry table at 0x104, 36-byte headers for all resources"

CORRECT FORMAT (confirmed May 2026):
  See Section 4 for the full layout. Summary:
  - [0x000] uint32 N
  - [0x004..0x104] 252-byte preamble + padding (zeros for custom bundles)
  - [0x104] (N+1) × 16-byte TOC entries; entry[N] = sentinel = copy of entry[0]
  - [toc_end] 20-byte res-0 header: {flags(4), zeros(8), data_sz(4), stream_sz(4)}
  - [toc_end+20] res-0 data bytes
  - [after res-0] resources 1..N-1: each 36-byte header + data

For a package-only bundle (N=1):
  toc_end = 0x104 + 2*16 = 0x124
  res-0 = the package resource blob (N_entries*28 + 5 bytes)
  No resources 1..N-1 exist

--------------------------------------------------------------------------------
9C.1 COBJ BINARY FORMAT (Stingray Compiled Binary Object)
--------------------------------------------------------------------------------

All render_config blobs are encoded as COBJ — Stingray's compiled key-value
binary format. It is a compact binary representation of a nested
object/array/string tree.

FILE LAYOUT:
  HEADER (8 bytes):
    uint32  root_type    — always 6 (object)
    uint32  root_offset  — byte offset of root object node from start of file

  NODE TYPES:
    Type 1 = uint32  (value stored inline as uint32 in vdata)
    Type 2 = float   (value stored inline as IEEE 754 float in vdata)
    Type 4 = string  (vdata = byte offset of null-terminated string from file start)
    Type 5 = array   (vdata = byte offset of array node)
    Type 6 = object  (vdata = byte offset of object node)

  OBJECT NODE:
    uint32  count
    count × 12-byte entries:
      uint32  key_ptr   — byte offset of null-terminated key string
      uint32  vtype     — type code (1/2/4/5/6)
      uint32  vdata     — inline value or offset

  ARRAY NODE:
    uint32  elem_type   — type code of all elements (or 0 if empty)
    uint32  count       — number of elements
    count × uint32:     — offsets (for type 5/6) or inline values (1/2)
    Special: {0, 0} = empty array

  STRINGS:
    Stored after all nodes, null-terminated, 4-byte aligned.
    Globally deduplicated — identical strings share a single copy.

ENCODER IMPLEMENTATION NOTE:
  When building COBJ, array pointer offsets MUST be captured interleaved
  with writes. Capturing all offsets first (e.g. list comprehension before
  writing) produces wrong offsets because writes advance the buffer pointer.
  See render_config_tools.py::COBJEncoder for the correct implementation.

--------------------------------------------------------------------------------
9C.2 RENDER_CONFIG SCHEMA (top-level object keys)
--------------------------------------------------------------------------------

Top-level object has one key: "resource_generators" → array of objects
Each generator object has:
  "type"          string  — type of modifier (see below)
  "name"          string  — unique name for this generator
  "output"        string  — output target slot name (some types require this)
  "input"         string  — input texture slot name (optional)
  "shader"        string  — shader to use (optional, see format below)
  "draw_as_quad"  uint32  — 0 or 1 boolean flag (optional)
  "target"        string  — for generate_mips: texture slot to generate mips for

  (Additional keys possible for other modifier types not yet seen)

--------------------------------------------------------------------------------
9C.3 KNOWN MODIFIER TYPES
--------------------------------------------------------------------------------

"generate_mips":
  Generates mipmaps for a texture render target.
  Required fields: "type", "name", "target"
  Example: { type="generate_mips", name="gen_mips_target", target="texture_slot_name" }

"fullscreen_pass":
  Renders a full-screen shader pass (post-process effects, blit, etc.)
  Required fields: "type", "name", "output"
  Optional fields: "input", "shader", "draw_as_quad"
  Example: { type="fullscreen_pass", name="tonemap", output="screen",
             input="hdr_target", shader="shaders/tonemap:HDR:ACES" }

Shader field format:
  "shader_name"                  — shader with no defines
  "shader_name:DEFINE1:DEFINE2"  — shader with preprocessor defines

9D. FONT RESOURCE FORMAT  *** NEW — Confirmed May 2026 ***
================================================================================

Font resources (.font) contain bitmap-font glyph metrics for in-game text rendering.
Type hash: 0x9EFE0A916D35FA19  (MurmurHash64 of "font")

File size: 8260 bytes for the default Gauntlet monospaced font (256 glyphs).
Formula:  HEADER_SIZE + glyph_count × GLYPH_SIZE = 68 + 256 × 32

--------------------------------------------------------------------------------
9D.1 HEADER (68 bytes)
--------------------------------------------------------------------------------

HEADER_FMT = '<I5fII7fII'   (68 bytes)

  Offset  Size  Field              Value (sample)
  ------  ----  -----              ------
  0x00    4     unknown_0          5
  0x04    4     line_height        96.0   (pixels per line)
  0x08    4     ascent             96.0
  0x0C    4     cap_height         75.0
  0x10    4     tex_scale_x        0.0009765625  (= 1/1024, atlas width)
  0x14    4     tex_scale_y        0.0015625     (= 1/640, atlas height)
  0x18    4     glyph_count        256
  0x1C    4     pad0               0
  0x20    4     bounds_max_x       990.0
  0x24    4     bounds_min_y       0.0
  0x28    4     unk_f2             29.0
  0x2C    4     unk_f3             60.0
  0x30    4     unk_f4             10.0
  0x34    4     unk_f5             17.0
  0x38    4     default_advance    45.0   (all glyphs advance 45px → monospaced)
  0x3C    4     glyph_count2       256    (redundant copy)
  0x40    4     pad1               0
  
  Total: 68 bytes

--------------------------------------------------------------------------------
9D.2 GLYPH RECORDS (32 bytes each)
--------------------------------------------------------------------------------

GLYPH_FMT = '<7fI'   (32 bytes)

  Offset  Size  Field        Description
  ------  ----  -----        -----------
  0x00    4     x            Atlas UV — left edge (pixel units, not normalized)
  0x04    4     y            Atlas UV — top edge
  0x08    4     w            Atlas UV — width
  0x0C    4     h            Atlas UV — height
  0x10    4     x_offset     Glyph bearing X (pixels from pen position)
  0x14    4     y_offset     Glyph bearing Y (pixels from baseline)
  0x18    4     x_advance    Advance width (45.0 for all glyphs = monospaced)
  0x1C    4     char_code    Unicode codepoint (uint32)

Glyphs are stored in atlas-packing order (NOT sorted by char_code).
char_codes span ASCII 0x20–0x7E plus Latin Extended (accented characters).

9E. ANIMATION RESOURCE FORMAT  *** NEW — Confirmed May 2026 ***
================================================================================

Animation resources (.animation) contain compressed skeletal animation tracks.
Type hash: 0x931E336D7646CC26  (MurmurHash64 of "animation")

--------------------------------------------------------------------------------
9E.1 HEADER (16 bytes)
--------------------------------------------------------------------------------

  Offset  Size  Field           Description
  ------  ----  -----           -----------
  0x00    4     flags           0 (observed)

9F. STRINGS RESOURCE FORMAT  *** NEW — Confirmed May 2026 ***
================================================================================

Strings resources (.strings) contain localised game text.
Type hash: 0x0D972BAB10B8CD51  (MurmurHash64 of "strings")

Typical blob size: 171,115 bytes (contains 3422 string entries).

--------------------------------------------------------------------------------
9F.1 OUTER LANGUAGE INDEX (132 bytes)
--------------------------------------------------------------------------------

11 × 12-byte entries, one per supported language:

  Offset  Size  Field               Description
  ------  ----  -----               -----------
  0x00    4     language_bitmask    1=English, 2=French, 4=German, 8=Spanish,
                                    16=Italian, 32=Portuguese, 64+32=Polish,
                                    128=Russian, 256/512/1024=unknown
  0x04    4     bundle_abs_offset   Absolute byte offset in the DECOMPRESSED bundle
                                    body. Points to a per-language string override
                                    table elsewhere in the bundle (NOT in this blob).
  0x08    4     zero                Always 0.

The bundle_abs_offset values are bundle-global positions — to decode per-language
overrides you need the entire decompressed bundle context.

--------------------------------------------------------------------------------
9F.2 INNER STRING INDEX (variable length)
--------------------------------------------------------------------------------

Starts at byte 132. N × 8-byte entries:

  uint32  hash32        MurmurHash32 of the string lookup KEY
  uint32  pool_offset   Byte offset of the string value within the String Pool

Number of entries N is determined automatically (strings_tools.py uses a heuristic:
finds the transition from binary pairs to sustained printable text).
For the Gauntlet sample: N = 3422, inner index ends at byte 27508.

--------------------------------------------------------------------------------
9F.3 STRING POOL (starts after inner index)
--------------------------------------------------------------------------------

Null-terminated UTF-8 strings packed together. Multiple inner index entries
may point to different offsets within the SAME contiguous string bytes
(suffix-sharing for space savings). Each pool_offset is relative to the
pool start position (first byte after the inner index).

The pool contains strings from the DEFAULT language (English).
Per-language overrides exist at the bundle_abs_offset positions in the outer index.

Example (first 5 entries from Gauntlet sample):
  0x3e85f3ae → "orko or whatever your name was. Never deny an elf his gold."
  0x00044fef → "turning out to be quite the picnic."
  0x00198681 → "ire Boots duration increased by 20%"

Tool: resource_tools/strings_tools.py — decodes outer + inner index + string pool.
Note: encode not yet implemented (bundle_abs_offset values require bundle context).

10. MODDING APPROACH
================================================================================

Based on dev information and analysis, here's the approach for modding:

Option A: Edit Existing Bundle (In-Place Replacement)
  1. Decompress bundle using zlib
  2. Find and replace texture data (maintain same size!)
  3. Recompress bundle
  4. Replace original file (backup first!)
  
  Tool: replace_textures_v4.py handles this workflow

Option B: Inject New Bundle (Preferred for larger mods)
  1. Create a new bundle with modified resources
  2. Add entry to bundle_database.data (at END for priority)
  3. Game loads your bundle's resources instead of originals

Texture Replacement Steps:
  1. Extract all textures to PNG using extract_all_textures.py
  2. Find the texture you want to modify (check normals/ and base_color/)
  3. Edit the PNG (maintain exact dimensions!)
  4. Use replace_textures_v4.py to inject the modified texture back
  5. Backup original bundle and replace with modified version

Important Size Constraints:
  - DDS texture data must be EXACT same size as original
  - DXT1: 8 bytes per 4x4 block = (width × height) / 2
  - DXT5/ATI2: 16 bytes per 4x4 block = (width × height)
  - Mipmaps also included - maintain full mipchain size

================================================================================
11. KNOWN LIMITATIONS
================================================================================

1. Size Constraints for In-Place Replacement
   - Replacing textures requires maintaining exact same size
   - Changing texture dimensions requires updating metadata
   - Using replace_textures_v4.py allows any size but may break streams
   
2. Hash Dependencies  
   - All resource references use hashes, not readable names
   - Must compute correct MurmurHash64 for any new resources

3. Compiled Resources
   - Non-texture resources (Lua, units, etc.) are compiled
   - No easy way to decompile without engine source

4. Engine Version
   - Gauntlet uses older Bitsquid version
   - Tools from newer games may not be compatible

5. Stream File Dependencies (CRITICAL)
   - Level bundles have .stream files with texture mipmap data
   - Modifying bundles with streams causes level loading to freeze
   - Stream file format not yet fully documented
   - WORKAROUND: Only modify bundles WITHOUT .stream files
   
6. Bundles Safe to Modify (no .stream file):
   - 07c9b8511b5aff2e (122 textures) - Menu/UI ✓
   - 07cdebae91f29fae (324 textures) - Lobby/Characters ✓
   - feec2c9522011d13 (128 textures)
   - 1bbcb9610a009446 (131 textures)
   - Many smaller bundles

7. Bundles Requiring Stream Support (DO NOT MODIFY YET):

13A. BUNDLE LOADING WITHOUT MODIFYING bundle_database.data
================================================================================

UNDERSTANDING THE PROBLEM
-------------------------

Gauntlet's resource system normally requires:
1. Bundle file in contents/ folder
2. Entry in bundle_database.data mapping resources to bundles
3. Package definition loaded at game start

However, there are ways to work around this:

METHOD 1: TEXTURE REPLACEMENT (Recommended - No DB Modification)
----------------------------------------------------------------
Instead of adding NEW bundles, REPLACE textures in EXISTING bundles.
The bundle is already registered, so no DB changes needed!

  1. Create your replacement texture as DDS
  2. Name it with the hash of the texture you're replacing: <hash>.dds
  3. Use replace_textures_v4.py to inject into the original bundle
  
  Example:
    # Replace warrior diffuse texture
    python replace_textures_v4.py "contents/0164ad48615ba9ed" my_textures/
    # Where my_textures/ contains: 67111d9e39e1cabc.dds

  Advantages:
    - No bundle_database.data modification
    - No package changes needed
    - Works immediately
    - Easy to revert (restore .backup)

METHOD 2: VERMINTIDE-STYLE MOD LOADING (How Vermintide Does It)
---------------------------------------------------------------
Vermintide 2 uses a custom mod framework with its own bundle format:

  1. .mod file (Lua config) defines mod entry point and packages
  2. mod_bundle contains all resources with signature 0xF0000006
  3. Mod framework (VMF) hooks into game and loads bundles dynamically

The key is the mod framework itself:
  - VMF registers a hook on ResourcePackage.load()
  - Intercepts package loading and injects mod bundles
  - Uses its own resource registry separate from bundle_database

For Gauntlet, this would require:
  - A DLL injection or similar to intercept resource loading
  - Custom bundle loading code that bypasses the normal DB check

METHOD 3: GAUNTLET'S BUILT-IN PACKAGE MANAGER (Experimental)
------------------------------------------------------------
Gauntlet HAS the same PackageManager as Vermintide! In game.lua:

  _G.SPLASH_PACKAGES = {
      "resource_packages/scripts_base",
      "resource_packages/scripts_gui",
      "resource_packages/menu",
      "modules/menu/resources",
  }

The PackageManager.load_package() function:
  local package = Application.resource_package(path)  -- Looks up in DB
  ResourcePackage.load(package)
  ResourcePackage.flush(package)

CRITICAL LIMITATION: Application.resource_package() queries bundle_database!
The ONLY way around this is to either:
  a) Modify bundle_database.data (add_bundle_to_db.py does this)
  b) Hook at the C++ level (requires DLL injection)
  c) Replace resources in existing bundles (METHOD 1)

METHOD 4: ADD TO EXISTING BUNDLE (Hybrid Approach)
--------------------------------------------------
If you must add NEW resources, add them to an EXISTING bundle:

  1. Decompress an existing bundle
  2. Append your new resources to the resource list
  3. Update the entry table and hash table
  4. Recompress the bundle
  5. Update bundle_database.data with the new resources

This modifies both the bundle AND the database, but only touches
one database entry rather than adding a new one.

RECOMMENDED APPROACH FOR GAUNTLET
---------------------------------
Given Gauntlet's architecture, the practical options are:

1. TEXTURE REPLACEMENT - No DB changes, uses proven tools
2. DB MODIFICATION - Use add_bundle_to_db.py (one-time change)
3. DLL/LOADER HACK - Intercept C++ resource loading (complex)

For texture mods: Use Method 1 (replacement)
For new content: You MUST modify bundle_database.data

--------------------------------------------------------------------------------
TEXTURE FORMAT (type hash: 0xCD4238C6A0C69E32)
--------------------------------------------------------------------------------

Gauntlet stores textures as RAW DDS files (starts with "DDS " magic).

Creating a texture for a bundle:
  1. Create/edit image in any image editor (PNG, TGA, etc.)
  2. Convert to DDS with proper format:
     
     texconv -f DXT5 -m 8 -y my_texture.png
     
     Common formats:
       DXT1 - Opaque textures, 4 bits/pixel (no alpha)
       DXT5 - Textures with alpha, 8 bits/pixel
       ATI2 - Normal maps, 8 bits/pixel (better quality)
  
  3. Rename to the path hash: <hash>.dds
  
     Example: warrior_diff.dds -> 67111d9e39e1cabc.dds
     (calculate hash: python create_full_bundle_system.py hash "characters/avatar_warrior/warrior_diff")

DDS REQUIREMENTS:
  - Power-of-2 dimensions (128, 256, 512, 1024, etc.)
  - Include mipmaps (texconv -m generates them)
  - Match original format for replacements

--------------------------------------------------------------------------------
MATERIAL FORMAT (type hash: 0xEAC0B497876ADEDF)
--------------------------------------------------------------------------------

Gauntlet materials are BINARY, not text like Vermintide source files!

Binary Material Structure:
  Offset  Type     Description
  ------  -------  -----------
  0x00    uint32   Version (always 0x0A = 10)
  0x04    uint32   Section count
  0x08    uint64   Shader hash (MurmurHash64 of shader name)
  0x10    uint64   Zero padding
  0x18+   ...      Texture slot entries and settings

Each texture slot entry (variable position):
  uint32   Slot index
  uint32   ThinHash (upper 32 bits of slot name hash)
  uint64   Texture hash (MurmurHash64 of texture path)

Common shader hashes:
  "base"           -> 0x0EFE985F44B8E8A9
  "skin"           -> 0x8A9B67B2D8DB8E5A
  "gui"            -> 0x45A6B83292D3C1F0

Common ThinHashes (upper 32 of slot name):
  "diffuse_map"    -> 0xCD4238C6 (from full hash)
  "normal_map"     -> depends on full hash calculation
  "specular_map"   -> depends on full hash calculation

CREATING A NEW MATERIAL (ADVANCED):
  Since Gauntlet materials are binary, you need to:
  1. Extract an existing material as a template
  2. Modify the texture hash values
  3. Re-pack into binary format

  Or use decode_materials.py to understand the structure, then
  create a material builder (not yet implemented).

EASIER APPROACH: Replace texture in existing material's slot by
  replacing the texture itself (Method 1 above).

--------------------------------------------------------------------------------
UNIT FORMAT (type hash: 0xE0A48D0BE9A7453F)
--------------------------------------------------------------------------------

Units are 3D meshes with material slots and bone bindings.

Binary Unit Structure (summarized):
  - Header with counts (materials, bones, meshes)
  - Material slot table
  - Bone hierarchy
  - Mesh data (vertices, indices)
  - LOD levels

See FINDINGS section 9 for full unit format documentation.

CREATING A NEW UNIT:
  Would require a complete mesh exporter (not yet implemented).
  Current tools only EXTRACT units to OBJ, not create them.

--------------------------------------------------------------------------------
LUA FORMAT (type hash: 0xA14E8DFA2CD117E2)   [CORRECTED — was 0x997CBC2F3AECB2CF]
--------------------------------------------------------------------------------

Lua scripts are stored as either:
  a) Raw Lua source code (text)
  b) Compiled Lua bytecode (LuaJIT)

Gauntlet appears to use LuaJIT bytecode for shipped scripts,
but the engine can load source code during development.

CREATING A LUA RESOURCE:
  1. Write your Lua script
  2. Calculate path hash:
     python create_full_bundle_system.py hash "lua/my_mod/script"
     
  3. For source (if engine supports it):
     Just include the raw .lua file content
     
  4. For bytecode:
     luajit -b script.lua script.out
     Include the bytecode as resource data

PRACTICAL APPROACH:
  Use the custom/ folder Lua loading system instead!
  The bootstrap.lua framework loads Lua from files, bypassing bundles.

--------------------------------------------------------------------------------
PACKAGE FORMAT (type hash: 0xAD9C6D9ED1E5E77A)
--------------------------------------------------------------------------------

Packages define which resources should be loaded together.

Binary Package Structure:
  Offset  Type     Description
  ------  -------  -----------
  0x00    uint32   Flags (0 = standalone, other = has dependencies)
  0x04    uint32   Resource count
  0x08+   ...      Resource entries

Each resource entry (16 bytes):
  uint64   Type hash
  uint64   Name hash

CREATING A PACKAGE:
  from create_full_bundle_system.py import TYPE_HASHES, murmur_hash64
  import struct
  
  resources = [
      ("texture", "custom/my_texture"),
      ("material", "custom/my_material"),
  ]
  
  data = struct.pack('<II', 0, len(resources))  # flags=0, count
  for type_name, path in resources:
      type_hash = TYPE_HASHES[type_name]
      name_hash = murmur_hash64(path)
      data += struct.pack('<QQ', type_hash, name_hash)

The deps=0 flag is critical for standalone packages - see section 9B.

Located in: GauntletModLoader/src/bundle_manager.cpp

Flow:

9H. LEVEL RESOURCE FORMAT  *** NEW -- May 2026 ***
================================================================================

Type hash: 0xE7F01A5344F7C5A3  (MurmurHash64 of "level")
Sample file: Exports/samples/level_24abcdf4b1fb4d4a.level  (1136 bytes)
Tool: resource_tools/level_tools.py  (selftest: PASS, byte-exact)

--------------------------------------------------------------------------------
9H.1 OVERALL LAYOUT
--------------------------------------------------------------------------------

  HEADER (128 bytes):  16 x { uint32 field_a, uint32 field_b }

  Entry [0]:  { entities_offset, entity_count }
              e.g. { 128, 6 } = 6 entity records starting at byte 128

  Entry [1]:  { 1, unknown_size }  -- format version marker

  Entries [2..15]:  mixed section offsets and sentinel values
    - When field_a == field_b: sentinel marking empty/end sections
    - Other entries point to sub-sections within the file

  Known section offsets in the sample:
    @128  entity records  (count x 80 bytes)
    @608  resource path / layer name config section
    @720  small sub-table (64 bytes; likely LOD/section lookup)
    @784  empty
    @824  lighting / render environment (256 bytes; 4x4 identity matrices)
    @1080 index/offset back-references
    @1088 sentinel (field_a == field_b)

--------------------------------------------------------------------------------
9H.2 ENTITY RECORDS (80 bytes each)
--------------------------------------------------------------------------------

  Entities with template_hash != 0 are PLACED UNITS:

    Offset  Size  Field           Description
    ------  ----  -----           -----------
     0       8    entity_id       uint64: unique instance hash (0 = anonymous)
     8       8    template_hash   uint64: MurmurHash64 of unit/prefab name
    16       8    flags           uint64: unknown, usually 0
    24      12    position        float[3]: world XYZ position
    36       8    _pad_0          unknown floats (usually 0)
    44      12    rotation_abc    float[3]: rotation components
    56       4    scale           float: uniform scale (1.0, 8.0, 64.0 observed)
    60       4    scale_w         float: secondary scale component
    64       8    _pad_1          unknown floats
    72       8    _tail_hash      uint64: extra hash/component reference

  Entities with template_hash == 0 are SPECIAL ENTITIES (world/env settings).
  Their @24..71 region stores hashes rather than floats (preserved as raw hex).

  Rotation encoding: three floats, likely a partial basis vector.
  Values observed: (-0.707, -0.707, 1.0), (0.0, 0.0, 0.0)
  NOT a standard quaternion (4 floats). Full decode TBD.

--------------------------------------------------------------------------------
9H.3 RESOURCE CONFIG SECTION  (@608 in sample)
--------------------------------------------------------------------------------

  uint32 descriptors interleaved with Pascal-style null-terminated strings:
    { uint32 str_len_incl_null, char[str_len] null-terminated-string }
    Strings are padded to 4-byte boundary.

  Observed strings:
    'core/rendering/default_outdoor'  -- sky / render environment preset
    'default'                         -- default layer name

--------------------------------------------------------------------------------
9H.4 EDITING NOTES
--------------------------------------------------------------------------------

  To MOVE a placed unit:  edit position[0], position[1], position[2]
  To CHANGE a unit type:  edit template_hash to target unit name hash
  To SCALE a unit:        edit scale (float)
  To CHANGE sky preset:   needs full config-section parser (TBD)

  3) manifest.json consistency gate (if manifest exists):

     - manifest resource_count must match bundle.ini ResourceCount.
     - Mismatch causes bundle skip.

  4) Stream gate:
     - HasStream=true requires source .stream file.
     - HasStream=false allows empty .stream creation at target.

  5) Duplicate patch-set guards:
     - duplicate bundle hash and duplicate package hash collisions are rejected
       in preflight patch queue.

validated by loader; runtime payload integrity is still enforced by engine load.

15H. .UNIT FILES — WHAT WE NOW KNOW (WORKING FIELD GUIDE)
--------------------------------------------------------------------------------

This section consolidates the current best understanding of Gauntlet `.unit`
runtime payload behavior from byte-level analysis and live in-game probes.

1) PRACTICAL MENTAL MODEL (REQUIRED FOR MODDING)
------------------------------------------------

Think of a `.unit` as three layers:

  A) Mesh block(s) at file start
     - Vertex buffer, index buffer, shapes, bbox, material strings.
     - This is where visible geometry is encoded.

  B) Post-mesh trailer metadata
     - Variable length, required by runtime behavior.
     - Encodes additional identity/dependency records.

  C) Tail identity record (near file end)
     - Includes an 8-byte hash-like reference field.
     - Not safely editable in isolation.

Key consequence:
  A valid mesh block alone is NOT sufficient for safe runtime spawn.


2) VERIFIED BASE STRUCTURE (MESH BLOCK)
---------------------------------------

Confirmed parser-compatible layout at file start:

  uint32 signature = 0x00010090
  uint32 mesh_count
  repeated per mesh:
    uint32 vertex_buffer_size
    bytes[vertex_buffer_size] vertex_data
    uint64 padding
    uint32 vertex_count
    uint32 vertex_stride
    uint32 element_count
    element_count * 17-byte element descriptors
    12-byte padding
    uint32 total_index_count
    uint32 index_buffer_size
    bytes[index_buffer_size] index_data
    uint32 shape_count
    shape_count * 16-byte shapes
    7 * float32 bbox
    uint32 material_count
    repeated: uint32 name_len + bytes[name]

Observed stable runtime-friendly vertex declaration:
  - stride 56
  - elements: POSITION, NORMAL, BINORMAL, TANGENT, UV


3) TRAILER FACTS (CRITICAL)
---------------------------

Verified across 582 sampled native units:

  - Trailer length is never zero in native samples.
  - Trailer length varies by unit family/content.
  - Simple effects family may use small trailer (361 bytes).
  - World/gameobject units commonly use larger trailers (e.g., 2134 bytes).

Critical coupling behavior:
  - Editing trailer identity hash field alone causes spawn crash.
  - Therefore trailer fields are interdependent and likely reference-coupled.


4) HASH/IDENTITY BEHAVIOR (PROVEN)
----------------------------------

  - `AddUtility.spawn_unit_path` is direct `World.spawn_unit(...)` path call;
    no short-name fallback in that code path.
  - Nevertheless, runtime result can appear native-like if internal unit
    metadata references native identity/dependency hashes.

Observed on `cube_from_template.unit`:
  - Preserved native hash: `0x8AEED77B10003A6C` (`gameobjects/food/ham_plate`)
    in trailer region.
  - Replacing this with custom hash only:
      * changed one 64-bit trailer field
      * produced spawn-time crash

Conclusion:
  - This field is not a free rename slot; it is coupled to other trailer
    records and/or companion resource keys.


5) WORKING/FAILING CONFIGURATIONS SUMMARY
-----------------------------------------

FAIL: minimal generated unit (no trailer)
  - package load freeze/hang risk

FAIL: effect-family 361-byte trailer used for world spawn
  - load may succeed, spawn unstable

PASS (spawn stable):
  - template-derived world-unit shell (`ham_plate` family trailer 2134 bytes)
  - mesh rewritten in-place
  - trailer identity left in stable state

FAIL (spawn crash):
  - same as above, but trailer self-identity hash rewritten to custom hash only

ACTIVE mitigation strategy:
  - keep crash-safe trailer identity
  - add bundled alias unit entry for referenced path/hash
    (`gameobjects/food/ham_plate`) so dependency resolution remains custom-side


6) GEOMETRY PIPELINE LESSONS
----------------------------

Initial issue:
  - vertex remap to dominant axis produced cube-like bounds, but not a real
    closed cube topology.

Improved probe:
  - force positions to true cube corners (8 unique positions, each axis in
    {-0.5, +0.5}).

Latest user-confirmed milestone:
  - Spawn now shows a cube in game.
  - Physics is applied at origin (expected from reused world-unit shell).
  - Remaining issue reported: missing top face.

Top-face response applied:
  - `cubify_unit_template.py` now rewrites index buffer to deterministic cube
    triangles (all 6 faces) and mirrored winding for culling robustness.
  - Bundle rebuilt/deployed with this topology fix.


7) WHAT MUST BE TRUE FOR A SAFE CUSTOM .UNIT TODAY
---------------------------------------------------

Minimum currently validated safe constraints:

  - Use a known-good world-unit trailer family as shell.
  - Keep runtime-accepted trailer identity coupling intact unless all linked
    trailer fields are updated together.
  - Maintain stride/elements expected by native family (56-byte P/N/B/T/UV).
  - Keep package resource entries and path hashes consistent.
  - Validate in game at two stages:
      1) package load stability
      2) world spawn stability + visual correctness


8) OPEN REVERSE-ENGINEERING TARGETS
-----------------------------------

Still required for fully independent custom units:

  - Full decode of world-unit trailer sections (especially 2134-byte family).
  - Identification of all fields coupled to trailer identity hash.
  - Deterministic encoder for trailer metadata (not template reuse).
  - Clean topology/material authoring path without native-shell dependencies.


9) CURRENT RECOMMENDED WORKFLOW (UNTIL FULL DECODE)
---------------------------------------------------

  1) Start from known-good world-unit shell.
  2) Rewrite mesh vertices (and now indices) only.
  3) Keep trailer coupling stable.
  4) Optionally provide alias resources for trailer-referenced paths in same
     package.
  5) Test load, then spawn, then visual correctness.

This is currently the highest-confidence path for iterative model experiments.

16. ★ CUSTOM ASSETS SOLVED (July 5, 2026) — THE COMPLETE RECIPE ★

END STATE, CONFIRMED IN-GAME: a fully custom unit (crane, 18,841 verts) spawned

THREE ROOT CAUSES, none of which was the novel hash:

  #1 TEXTURE — missing 4-BYTE TRAILER after the mip chain          (hang)
  #2 UNIT    — missing TRAILING SECTIONS + 32-byte footer          (native crash)
  #3 BINDING — unit binds material via FOOTER HASH, not the string (wrong look)

================================================================================
16.1 TEXTURE RESOURCE FORMAT (root cause #1)
================================================================================

A compiled texture resource (bundle data field, stream_size=0) is:

  [128-byte DDS header][full mip chain, top mip -> 1x1][4-BYTE TRAILER]

THE 4-BYTE TRAILER IS MANDATORY. Survey of all 23 food_units textures:
every single one has exactly +4 bytes after the computed mip chain
(values seen: 00000000, 4a07531f, be0fc23f — 00000000 works).
Without it, the loader worker never posts the opcode-1 completion message
-> resource never completes -> has_loaded stays false -> package never
onlines -> anything waiting on it hangs. THIS WAS "THE WALL" ALL ALONG.

DDS header must match native conventions:
  flags        0x000A1007  (CAPS|HEIGHT|WIDTH|PIXELFORMAT|MIPMAPCOUNT|LINEARSIZE)
  pitchLinear  top-mip linear size
  mips         full chain: floor(log2(max(w,h)))+1  (0 of 23 natives are 1-mip)
  pf_flags     0x4 (FOURCC), fourcc DXT1/DXT5/ATI2
  caps1        0x00401008  (COMPLEX|MIPMAP|TEXTURE)
  reserved1[60:76] NVTT signature: 'UVER' 00000000 'NVTT' 00010200 (v2.1.0)
               (native textures are NVTT-compiled; sig alone did NOT fix the
                hang — the trailer did — but include it to stay native-identical)

Hand-rolled DXT1/DXT5 encoders are ACCEPTED (our checker pixels render fine).

================================================================================
16.2 UNIT RESOURCE FORMAT (root causes #2 and #3)
================================================================================

A native .unit = [mesh section][trailing sections ~2KB][32-byte footer]:

  MESH SECTION (this part gltf_to_unit.py builds correctly):
    sig 0x00010090, mesh_count, vbuf, elements, ibuf, shapes, bbox,
    material_count x {u32 len, name string}
    -> the material STRINGS are SLOT LABELS ONLY (natives use e.g. "m_ham";
       murmur("m_ham") maps to NO resource — it is not the binding!)

  TRAILING SECTIONS (missing from scratch-built units = the crash):
    collision/physics actors ("a_collision"), FlowCallbacks data,
    sub-resource refs {u64 hash, FFFFFFFF sentinel}...
    A unit without these COMPLETES BRING-IN (it's a CPU copy) but the engine
    CRASHES NATIVELY at the later resolve/patch stage walking off the end.
    (This is why unit-only bundles "worked" in earlier tests: the crash
    path only runs when the package fully onlines/flushes.)

  FOOTER (last 32 bytes — root cause #3, the material binding):
    04 00 00 00 | 12 zero bytes | u64 MATERIAL RESOURCE NAME HASH | 8 zero bytes
    Patch unit[len-16:len-8] to bind any material. Every native unit ends in
    zeros; a unit ending mid-string is malformed.

WORKING BUILD PATH (proven):
  1. Extract a native unit as template (used: ham_plate 0x8aeed77b10003a6c,
     8,660 B, trailer 2,134 B, from food_units cd241d5192024482).
  2. glb_to_template_unit.py <template.unit> <mesh.glb> <out.unit> [scale] [label]
     -> splices custom geometry into the template, preserves trailer VERBATIM.
  3. Patch footer hash -> your material resource name hash.
  Template physics/collision/flow come along; pick a template whose material
  shader suits the mesh.

NATIVE NAMING CONVENTION: a unit and its material share the same resource
name (gameobjects/food/ham_plate names BOTH the unit and material resource).
Custom paths (units/custom/..., materials/...) work fine — nothing parses
the path; the footer hash is the only coupling.

PACKAGE RESOURCE BLOB:
  u32 count + count x {u64 type_hash, u64 name_hash, u32 depcount=0} + 0x01

BUNDLE BODY (replace_textures_v4.py parse_bundle/rebuild_simple_bundle/

16.5 LOADING RULES (verified)
================================================================================

- ALWAYS ASYNC: Game:load_package(path, false). flush=true busy-waits
  WaitForSingleObject(INFINITE) on worker completion -> any defect = permanent
  freeze with no log and no dump.
- LOAD SCREEN (StateLoadGame) pumps the streamer: hook on_enter to issue the
  load, poll in pre_update. Install state hooks from a require hook, and use
  rawget(_G,"StateLoadGame") — strict.lua ERRORS on undeclared global reads
  (crashed boot once).
- IN-GAMEPLAY async ALSO completes (Game.update pumps package_manager:update()
  every frame — the material bundle onlined mid-gameplay). The idle MAIN MENU
  does NOT pump. Never load big packages at the menu.
- Game:is_package_online(path): nil = never requested, false = loading,
  true = online. Spawn only when online.
- A failing GPU resource does not error — it HANGS the load pipeline. A
  malformed unit CRASHES natively with no dump. Treat hang-vs-crash as signal:
  hang = texture-class problem, silent crash = unit-class problem.

================================================================================
16.6 THE EXPERIMENT CHAIN THAT CRACKED IT (methodology)
================================================================================

Each test = one game launch; every hypothesis isolated ONE variable:

  1. 1-mip checker, novel hash ................ HANG   (baseline failure)
  2. Full 8-mip checker ....................... HANG   (mips NOT the fix)
  3. 8-mip + NVTT reserved signature .......... HANG   (sig NOT the fix)
  4. HAM'S EXACT BYTES under our novel hash ... ONLINE  << disproved the
     "novel hashes have no render slot" theory in one shot
  5. Ham header + OUR pixels (no trailer) ..... HANG   (pixels innocent)
  6. Ham header + our pixels + 4B TRAILER ..... ONLINE  << TEXTURE SOLVED
  7. Full 4-res bundle (old scratch unit) ..... NATIVE CRASH
  8. Sequenced bisect: A=pkg+unit+tex loads first, B=pkg+material only after
     A onlines. Crash BEFORE "A ONLINE" ....... UNIT is the crasher
  9. Template-spliced unit (ham trailer) ...... A=true, B=true, SPAWNS,
     renders with ham material (footer still ham_plate's)
 10. Footer hash patched to our material ...... CHECKER RENDERS. DONE.

THE GREAT CONFOUND (why this took months): overriding a NATIVE hash "works"
because the engine reuses the already-resident boot copy — custom bytes never
actually go through bring-in. So every byte-format bug stayed invisible until
a truly novel resource forced a real load. (Also explains why the magenta
ham_diff override "onlined but didn't change appearance".)

DEBUGGING PATTERN THAT WORKED: swap known-good native bytes under the novel
name to split name-vs-bytes, then binary-search the byte diff (header vs
pixels vs trailer). All three root causes were plain byte differences vs
native resources. Byte-diff EVERYTHING against natives first; disassemble
second.

17. RESOURCE / BUNDLE NAME RECOVERY (MurmurHash64A)
================================================================================

17.1 THE HASH
  - Every bundle filename, resource name and package path is
    MurmurHash64A(path, seed = 0) over the ASCII bytes of the LOWERCASE path
    (64-bit lanes, little-endian). Confirmed bit-for-bit against the game for
    bundle names, resolved resources and texture references.
  - Names carry NO extension: the build tool strips every trailing extension
    (foundation/scripts/common.lua clean_filepath():
    `filename,count = string_gsub(filename, "%.%w+$", "")` repeated until
    count == 0) and normalises `\` -> `/`.
  - The TOC only stores hashes, so a name is recovered either from a text
    source (Lua / ini / embedded binary strings) or by brute force.

17.2 NAME SOURCES - THE generate_*.lua SCRIPTS ARE THE MAP
  foundation/scripts/generate_*.lua run at build time to auto-generate name
  lists. Each one documents how a resource family is named:

  generate_shader_libraries.lua
      scans `<source>/**/*.shader_source`; name = clean_filepath(file, root);
      sorts the list; rewrites the block between `// <SHADER_LIBRARIES>` and
      `// </SHADER_LIBRARIES>` inside the *render_config* resource as
      `shader_libraries = { ... }`.
      => shader_library_group names are PATHS (`core/rendering/<group>`);
         leaf shader_library names are BARE basenames (`fxaa`, `terrain`,
         `debug_gbuffer`, `beckmann_distribution_lut`, `omni_light_debug_lights`).
      => group basename == the matching leaf library name for many entries
         (`core/rendering/fxaa` <-> `fxaa`).

  generate_elias.lua
      for every melody dir (`resource_packages/elias/<name>`) transcodes
      `<melody>/audio/*.wav` -> `.ogg` -> renamed `.ugg`, then writes
      `<melody>.package` (SJSON) listing every ugg path.
      => ugg resource name = `<melody_dir>/audio/<source-wav-name>` (the `.ugg`
         is stripped). The source .wav file names are NOT shipped and are not
         referenced anywhere in Lua, which is why ugg (144) stays unresolved.
      => confirms ugg = Ogg voice lines (`resource_packages/elias/*_adventure`,
         `*_labyrinth`, `*_arena`).

  Other generators (mine them as vocabulary, they are name tables):
      generate_animation_events_lookup.lua (animation_event names),
      generate_unit_paths / unit_lookup / unit_data_lookup /
      unit_path_to_components (unit paths),
      generate_short_file_paths_lookup / file_lookup / project_path,
      generate_level_package / resource_package / slayer_resource_packages,
      layout lookup (lua/dungeon/layouts/lookup.lua -> quilt/arena paths),
      settings/vo_triggers.lua (voice-over trigger list).

  The render_config resource itself (bundle 1a9c33dcd0301dfd, 27,412 B) embeds
  the full `shader_libraries` array AND the shading-graph node names as plain
  ASCII: a machine-readable vocabulary of render words.

17.3 A NEW LEVER - SCAN RESOURCE BODIES FOR EMBEDDED STRINGS
  scan_bundle_strings.py walks every bundle, parses the resource table, and
  harvests printable ASCII runs from every resource body (173,664 distinct
  plausible strings). Some bodies reference names in text.
  - 42 strings were themselves unsolved resource names, e.g.
      shader_library_group: core/rendering/{additive,base_dx11,base_voxelizer,
        canvas,color_grading,debug_gbuffer,distort_access,fog,
        framebuffer_distort,fxaa,light_bake,mixer,multilayer,player_marker,
        terrain}
      shader_library: fxaa, color_grading, linearize_depth, global_lighting,
        ao_cone_trace, shadow_cutter, omni_light(_debug_lights),
        gbuffer_debug, downscale_depth, ssao_upscale, dof_near_coc,
        beckmann_distribution_lut, terrain_undergrowth, terrain_editor_brush,
        framebuffer_distort, debug_render_voxels, debug_gbuffer, terrain
      texture: core/rendering/nft, core/rendering/vo_rotation
      unit:    blocks/d01_crypt/walls/crypt_wall_door_01_4c
      material: characters/boss_mummy/boss_mummy_hole
  - The dump also doubles as a ~109 k-word candidate/vocabulary list, which is
    what finally pushed shader_library_group over the line (the group list in
    render_config plus the basename rule).

17.4 TOOLCHAIN - Scripting/hashcracker (Rust)
  Multithreaded MurmurHash64A brute-forcer (rayon, offline cargo build,
  -C target-cpu=native), ~200-260 M candidates/s on 12 cores.
    prepare.py    -> data/{targets,dirs,names,prefixes,suffixes}.txt
    crack         -> template expansion; `%X` slots bound with --list X=FILE.
                     IMPORTANT: a slot letter is LOCKED, so `%a_%a` repeats one
                     word; use `%a_%b` for a cross product.
    --candidates  -> test a plain candidate list (used for the string dump)
    --matches F   -> append-only, deduped TSV `<hash-hex><TAB><name>` (streamed)
    --exclude F   -> skip solved hashes
    mutate        -> byte-level mutation to fixpoint (~10x faster than v1)
    mine          -> aho-corasick dictionary pruning
  Results feed Scripting/GauntletGameDigging/resource_name_overlay.json via
  merge_matches.py; list_game_bundles.py then regenerates bundle_manifest/*.

17.6 WHY THE REMAINDER RESISTS
  Every family we have checked derives its name from a SOURCE FILE that is not
  shipped and is not referenced in any readable text:
    - shader_library (leaf): the `.shader_source` filenames.
    - ugg: the audio `.wav` filenames.
    - animation (1,243 unique): the clip names come from the binary `.unit` /
      animation blobs; the 217 `animation = "x"` Lua clip names give 0 hits in
      every shape tried (`<dir>/<clip>`, `animations/<clip>`, bare `<clip>`).
    - texture / material: names live in binary material/level payloads; the
      material->texture graph, global dir x token x suffix sweeps and mutation
      to fixpoint are exhausted.
  Brute force only helps where a name is a *recombination* of words that DO
  appear in text (which is what cracked the shader groups, quilts, levels,
  equipment, decals, map suffixes, etc.).

17.8 TIER-1 RETEST PASS (extension semantics, binaries, graph, mutation)
================================================================================
  Re-ran the whole pipeline against the now-1,900-name overlay and fixed three
  blind spots in our own tooling.

  (a) clean_filepath() re-test  -> +2.
      The bundle-body string dump (scan_bundle_strings.py) had only ever tested
      strings VERBATIM. The engine strips every trailing extension before
      hashing, so any `.../foo.norm.dds`-style string could never match. Re-ran
      the dump through clean_filepath semantics (strip `.ext` repeatedly, `\`->`/`,
      drop a leading dir component): 174,722 variants -> recovered
      `characters/boss_mummy/boss_mummy_hole` and
      `blocks/d01_crypt/walls/crypt_wall_door_01_4c`, which the original scan had
      PRINTED as hits but never written to matches.tsv. New tool:
      scan_binaries.py (binaries), plus the variant list is now fed through
      `crack --candidates` so hits are always recorded.

  (b) game binaries -> 0.
      prepare.py only kept the LAST `/`-segment of a path-like string from
      gauntlet.exe/*.dll. scan_binaries.py keeps whole strings and expands them
      (ext-strip, every known root prefix): 855,744 candidates from 13 binaries
      -> 0 hits. The exe/DLLs carry IDENTIFIERS (`render_config`,
      `shader_library`, `elias_theme_*`), not resource paths. elias.dll (the
      dialogue system) contains no .wav/.ugg names either.
      .stream files are simply `<bundle-hash>.stream` -> no name material.

  (c) material -> texture graph -> +1.
      derive_textures.py re-run with the current overlay: only 1 new name. The
      reason is structural, not a bug: materials_database.json holds just 1,657
      decoded material records (a subset), of which 1,099 now have known names;
      most unknown materials reference textures that are themselves unknown, so
      the graph has no anchor to walk from.

  (d) mutate to fixpoint -> +106.
      84 + 18 + 4, then 0. Mutation is the single best value-per-second tool we
      have: it found e.g. `props/d01_common/fog_volume_swamp_01` and, notably, a
      NEW quilt field pattern `ox_ex_ix_ex` that the hand-written quilt grammar
      enumeration had missed. Lesson: prefer mutate over hand-built grammars.

  Net: 1,877 -> 1,986 names (+109).

17.10 foundation/scripts/ — THE AUTHORITATIVE SOURCE-TYPE MAP
================================================================================
  Every resource family is produced by a build script that scans a SOURCE file
  extension and writes the resource name as `clean_filepath(file, root)` (path
  minus every trailing extension, `\`->`/`). Absolutes are built as
  `root .. path .. "." .. type` (dependency_resource.lua), which is why the
  hash never sees an extension.

  Complete list of source extensions referenced by foundation/scripts:
      .unit        units            (generate_unit_paths / unit_lookup / unit_data_lookup)
      .level       levels           (generate_level_lookup / level_info / level_package)
      .lua         lua + units      (dependency_parser)
      .flow        flows            (dependency_parser)
      .texture     textures         (texture_sanity_checks)
      .material    materials        (validate_materials_texture_resources)
      .state_machine  state machines + animation EVENTS
                                      (generate_animation_events_lookup)
      .physics     physics          (unit_sanity_checks, nav_grid)
      .level_editor / .bsi / .package / .override_settings
      .shader_source  shader libraries (generate_shader_libraries)
      .wav -> .ugg  elias voice lines  (generate_elias)
      .shading_environment

  **THERE IS NO ANIMATION SOURCE EXTENSION.** The clip names live inside the
  per-unit `.state_machine` (and `.unit`) SJSON sources:
  generate_animation_events_lookup.lua reads `sjson.events` out of
  `*.state_machine` files. Those sources are NOT shipped (only `.lua` is in
  Gauntlet-Source-DO_NOT_EDIT), which is the definitive reason the animation
  leaf names cannot be recovered from any shipped text — it confirms §17.9
  empirically rather than by elimination.

  Bonus vocabulary extracted here:
      - validate_materials_texture_resources.lua holds the engine's 20 material

      local w = #u      -- quilt width  in cells
      local h = #r      -- quilt height in cells

  So a quilt name is <env>_quilt_<shape>__<up>_<right>_<down>_<left>__<variant>,
  the four groups being the cell rows of the four SIDES of a quilt piece, each
  cell one of  x (wall), e (through), i (entrance), o (exit).  The rule
  len(up) == len(down) == w and len(right) == len(left) == h is what makes the
  candidate space finite; observed side lengths are 1, 2, 3 and 5 (never 4).
  Variants are NN, NN_<mod>, or start_NN (crypt entrances).

  WHY THE EARLIER SWEEPS FOUND NOTHING: the vocabulary had been built from the
  side groups that appear in RESOLVED names.  Several 1-cell sides ("o", "i")
  never appear in any resolved piece, so codes such as o_e_i_e were unreachable.
  Enumerating the alphabet under the width/height rule found them immediately:

      crypt_quilt_smallroom__o_e_i_e__01
      crypt_quilt_smallroom__o_e_i_e__01_skeleton
      caves_quilt_smallroom__o_e_i_e__01
